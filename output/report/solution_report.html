Overview

What we built

A web application that takes a savings-account application from submission with documents to a final outcome. It applies the 17 rules of the specification exactly, screens sanctions and PEP lists, routes doubtful cases to a KYC Officer, and requires a different Compliance Officer to approve doubtful and high-risk cases. Every decision and every document view is audited.

1 · ApplicantFills the form (only the last 4 Aadhaar digits), uploads PAN, Aadhaar and an address proof as .txt or text-based PDF.
→
2 · ExtractionMock provider (supplied files) or our AI provider reads each document: type, fields, confidence. Optional Groq LLM.
→
3 · Rules R1–R17A pure, table-driven engine decides APPROVE / REVIEW / REJECT with reason codes, name score, risk and re-KYC date.
→
4 · PeopleClean cases open automatically; REVIEW goes to a KYC Officer (maker); a different Compliance Officer (checker) decides.

Technology

LayerChoice and why
FrontendReact 19, TypeScript, Vite, Tailwind with hand-built accessible components. One app with role-based screens; responsive down to phone width.
BackendNode.js, Express 5, TypeScript, Zod validation (the same schemas generate the OpenAPI contract). Modular monolith: one API, clear modules.
DatabasePostgreSQL 16 with Prisma migrations; audit table is append-only through a database trigger; Aadhaar limited to 4 digits by a constraint.
AIDeterministic classifier and extractor with OCR-error repair and calibrated confidence (fast, explainable, reproducible). Optional LLM (Groq openai/gpt-oss-120b or Anthropic) that only proposes, behind strict schemas.
QualityVitest + Supertest on a real test database, Testing Library, Playwright in Chrome, GitHub Actions CI, Docker Compose.
1 · Feature tour

Applicant

Applicants register, sign in, fill one form, upload documents and follow their case. They never see confidence scores, watchlist data or other people's applications; the server enforces this, not just the screen.

1 · Feature tour

KYC Officer (maker)

Officers work the review queue: highest risk first, then the longest waiting. They only see cases in review, awaiting the checker or awaiting new documents.

1 · Feature tour

Compliance Officer (checker)

Compliance Officers decide cases awaiting a checker, see the dashboard and audit trail, find any application, and maintain watchlists and rule configuration.

1 · Feature tour

On a phone, and for developers

Every screen fits a 390-pixel-wide phone without sideways scrolling; this is checked automatically for 14 screens in Chrome. The menu collapses behind a Menu button.

Security tests

  • No token → 401 on every protected route
  • Wrong role → 403; applicant on officer APIs → 403
  • Another applicant's case or document → 404, attempt audited
  • Maker cannot check own case → 403, even with both roles
  • Wrong state or lost race → 409; final statuses frozen
  • Masking of Aadhaar and PAN in lists, logs and exports
  • Prompt injection: document classified OTHER, no decision change
  • Uploads: size, type, encoding, binary content, scans, duplicates
  • Login lock-out with 429 after five failures; no user enumeration

Live checks with Groq

  • PDF PAN card plus two .txt files uploaded through Docker: every field read correctly at 0.95–0.97 confidence; 3 documents in about 4 s
  • Rules gave REVIEW with only ADDRESS_PROOF_STALE: correct, the sample bill is older than 90 days
  • AI summaries for real in-review cases in about 2 s, all within 80 words and with values from the case
  • Applicant attempting a checker decision → 403; submitting twice → 409

5 · Not built, and known limits
  • Officer correction rate (AI-4): corrections are stored as labelled feedback, but the supplied data has no officer feedback to compute a rate from.
  • LLM accuracy: Groq is used live for summaries and optional extraction; we spot-checked it but report no LLM accuracy figure.
  • Scanned images and photos: no OCR, because the Groq models available to us have no vision model. Text-based PDFs work.
  • Bonus ideas not built: highlighting the exact text span of each field, mock CKYC search, multilingual or transliterated names.
  • Simulated by design (out of scope): core banking, identity checks and watchlists are mocks with synthetic data. Performance figures come from one machine.
  • Our design choices: revocable server-side sessions and scrypt instead of JWT and bcrypt; the source is in backend/ and frontend/ rather than /code.
6 · How to run it

Run, test and regenerate

Start

cp .env.example .env      # fill the change-me values
npm run install:all
npm run db:up && npm run db:migrate
npm run db:seed           # data pack, demo users, processing
npm run dev               # API :3000, UI :5173

# or everything in Docker
docker compose up --build # UI on http://localhost:8080

Verify

npm run check             # types, lint, format, tests, builds
npm run e2e               # Chrome end-to-end (own database)
npm run outputs -- --fresh-db
npm run outputs:repeat    # determinism proof
npm run perf              # performance report
npm run design            # design docs and /prompt
npm run batch             # decisions_output.csv
